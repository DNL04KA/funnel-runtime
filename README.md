# Funnel Runtime

Мини-платформа для запуска, версионирования и анализа многошаговых веб-воронок.
Конфигурируемые экраны, A/B внутри версии, собственный приём событий, аналитика
по уникальным сессиям и откат версий без потери данных.

Тестовое задание, все данные вымышленные. Один репозиторий, fullstack TypeScript,
SQLite, без сторонних сервисов.

```
shared/   доменное ядро: схема конфига, условия, обход графа, валидация, A/B, обезличивание
server/   Express + SQLite: версии, сессии, события, аналитика, админ-API, генератор трафика
web/      React + Vite: воронка, страница управления версиями, дашборд
configs/  три JSON-конфига воронки (v1, v2 и конфиг второй итерации v3)
tests/    vitest: закрепление версии, A/B, дедупликация, публикация и откат, аналитика
demo/     сценарий записи демо-ролика (Playwright) и сам ролик
```

| Управление версиями | http://localhost:5173/#/admin |

## 1. Динамическая воронка

Во фронтенде нет ни одного захардкоженного экрана. `FunnelPage` рендерит то, что
вернул бэкенд, а `StepRenderer` — единственное место, которое знает про *типы*
шагов. Добавить экран = поправить JSON; добавить тип шага = добавить ветку в
рендерер и в валидатор.

Поддерживаются типы: `info`, `single_select`, `multi_select`, `number`, `result`.

**Переходы.** У шага есть `next` — либо id следующего шага, либо список правил:

```json
"next": [
  { "if": { "field": "role", "op": "eq", "value": "it" }, "goto": "integrations" },
  { "goto": "warehouses" }
]
```

Побеждает первое правило, чьё условие истинно; правило без `if` — безусловная
ветка. Условия поддерживают `eq/neq/in/nin/gt/gte/lt/lte/includes/excludes/
answered/empty` и композиции `all` / `any` / `not`.

**Навигацией управляет сервер.** Клиент отправляет ответ, сервер валидирует его,
сохраняет и сам вычисляет следующий шаг. Перепрыгнуть на недоступный шаг из
браузера нельзя.

**Прогресс считает только доступные шаги.** `computeProgress` склеивает уже
пройденную историю сессии с проекцией оставшегося пути (для неотвеченных
вопросов берётся безусловная ветка). Поэтому на вопросе об объёме заказов
счётчик показывает «Шаг 4 из 6», а после ответа «более 50 000» — «Шаг 5 из 7»:
появилась ветка с вопросом о бюджете.

**Состояние не теряется.** Источник правды — строка в `sessions` на сервере;
в `localStorage` браузера лежит только `session_id`. Поэтому:

- *refresh* — `GET /api/session/:id` возвращает текущий шаг и ответы;
- *повторное открытие страницы* — то же самое, даже если URL потерял параметры;
- *кнопка «Назад» браузера* — каждый шаг кладёт запись в `history`, обработчик
  `popstate` вызывает `POST /api/session/:id/back`, и сервер возвращает
  предыдущий шаг вместе с уже сохранённым ответом.

Если пользователь вернулся назад и сменил ответ так, что путь ушёл в другую
ветку, ответы брошенной ветки удаляются — иначе экран результата читал бы
значения, которых пользователь в этом прохождении не давал.

## 2. Версионирование и откаты

Конфиги лежат в базе, а не в бандле, поэтому публикация не требует передеплоя.

| Операция | Что делает | API |
| --- | --- | --- |
| Публикация | добавляет строку в `funnel_versions` со следующим номером | `POST /api/admin/versions` |
| Публикация без включения | то же, но указатель активной версии не трогается | то же, `activate: false` |
| Просмотр активной | номер + конфиг + граф переходов по каждому варианту | `GET /api/admin/overview`, `GET /api/admin/versions/:v` |
| Включение / откат | переставляет указатель в `funnel_active` | `POST /api/admin/activate` |

**Откат — это включение более ранней версии.** Отдельной операции нет: ничего не
удаляется, версии только добавляются. Если целевой номер меньше текущего,
действие записывается в журнал как `rollback`, иначе как `activate`.

**Закрепление версии за сессией.** При создании сессии в её строку пишется
`funnel_version` текущей активной версии. Дальше всё — отдаваемый конфиг,
вычисление переходов, запись событий, бакет в аналитике — читает это поле, а не
живой указатель. Следствия:

- старая сессия продолжается на старой версии и спокойно доходит до результата;
- новая сессия всегда стартует на текущей активной версии;
- в UI воронки появляется плашка «сессия продолжается на версии N, активна M».

**Валидация перед публикацией.** Конфиг не попадёт в базу, если в нём есть
несуществующий `goto`, условие на поле, которое никто не собирает, шаг без
`next`, недостижимый `result`, дубли id опций и т. п. Проверяется не только
исходный конфиг, но и каждый вариант после применения патчей — иначе удаление
экрана для варианта B могло бы оставить висящий переход.

## 3. A/B-эксперимент

Вариант назначается **на бэкенде** в момент создания сессии и сохраняется в её
строке. Назначение детерминировано: `FNV-1a(experiment_key + ':' + session_id)`
→ число в `[0,1)` → вариант по `split`. Одинаковый `session_id` всегда даёт
одинаковый вариант, таблица соответствий не нужна, refresh ничего не меняет.

Override для проверки: `?variant=B`. Он фиксируется за сессией
(`variant_source: "override"`) и подсвечивается в UI; некорректное значение
игнорируется, и вариант назначается обычным образом.

Конфиг для варианта **резолвится на сервере**: клиент получает уже плоский
конфиг, в котором применены `overrides` (замена полей шага), `removeSteps`
(удаление шага с перевязкой входящих переходов) и `stepOrder` (канонический
порядок для дашборда). Подменить вариант из браузера нельзя: `funnel_version`,
`variant` и UTM-метки у события берутся из строки сессии, а не из тела запроса.

### Гипотеза и основная метрика

Актуальный эксперимент — в активной версии; гипотеза каждой версии лежит в
`experiment.hypothesis` и видна на странице управления.

**v1 — `exp_result_cta_v1`, основная метрика `cta_ctr`.**
Вариант A завершает воронку расчётом стоимости («Получить расчёт»), вариант B —
живым демо («Записаться на демо»). Гипотеза: обещание конкретной цифры снижает
воспринимаемый риск сильнее, чем обещание встречи, поэтому A даёт более высокий
CTR основного CTA при сопоставимой конверсии в результат.

**v2 — `exp_priorities_first_v2`, основная метрика `result_rate`.**
Вариант B переносит вопрос «что закрыть в первую очередь» сразу после роли, до
вопросов об объёме и бюджете. Гипотеза: разговор о собственных болях вовлекает
сильнее, чем разговор о цифрах, поэтому B доводит до результата больше сессий —
особенно на дорогой ветке с вопросом о бюджете. Контрольная метрика — `cta_ctr`:
если она просядет, выигрыш в конверсии получен за счёт хуже квалифицированного
трафика.

**v3 — `exp_short_path_v3`, основная метрика `result_rate`.**
Вариант B лишается экрана с количеством складов — путь короче на шаг. Гипотеза:
это поле не влияет на подбор тарифа в верхней части воронки, значит его можно
убрать и выиграть на конверсии, не потеряв релевантность. Контрольная метрика
снова `cta_ctr`.

Дашборд показывает обе метрики рядом и считает дельту в процентных пунктах к
варианту A. Статистической значимости он не считает — см. «Ограничения».

## 4. Событийная система

`POST /api/events` принимает пачку и отвечает **200 с вердиктом по каждому
событию**, а не падает целиком:

```jsonc
// запрос
{ "events": [ { "event_id": "...", "session_id": "...", "event_type": "step_viewed",
                "client_ts": "2026-10-07T10:00:00.000Z", "step_id": "role", "props": {} } ] }

// ответ
{ "received": 3, "accepted": 1, "duplicates": 1, "rejected": 1,
  "results": [ { "index": 0, "status": "accepted",  "event_id": "..." },
               { "index": 1, "status": "duplicate", "event_id": "..." },
               { "index": 2, "status": "rejected",  "event_id": "...",
                 "error": "неизвестный event_type \"teleported\"" } ] }
```

### Типы событий

`session_started`, `step_viewed`, `answer_submitted`, `step_completed`,
`back_clicked`, `result_viewed`, `cta_clicked` и добавленный второй итерацией
`hint_expanded`.

Часть событий сервер пишет сам, чтобы их нельзя было потерять: `session_started`
— при создании сессии, `answer_submitted` и `step_completed` — внутри обработки
ответа, `back_clicked` — внутри обработки возврата. Остальные приходят с
клиента. У серверных событий детерминированный `event_id`, поэтому если клиент
пришлёт такое же событие, оно схлопнется с уже записанным.

### Поля события

| Поле | Источник | Комментарий |
| --- | --- | --- |
| `event_id` | клиент | первичный ключ, минимум 8 символов |
| `session_id` | клиент | неизвестная сессия → `rejected` |
| `event_type` | клиент | не из белого списка → `rejected` |
| `client_ts` | клиент | нормализуется в ISO; не дата → `rejected` |
| `server_ts` | сервер | время приёма |
| `funnel_version` | **сессия** | присланное клиентом игнорируется |
| `variant` | **сессия** | то же |
| `step_id` | клиент | может быть `null` |
| `utm_*` | **сессия** | зафиксированы при её создании |
| `props` | клиент | JSON, до 8 КБ |

### Инварианты

| Требование | Как обеспечено |
| --- | --- |
| Повторный `event_id` не создаёт дубль | `event_id` — PRIMARY KEY, вставка через `INSERT OR IGNORE`; `changes === 0` → `duplicate` |
| Приём пачкой | до 500 событий за запрос, одна транзакция |
| Повтор после timeout безопасен | ретрай той же пачки даёт `accepted: 0, duplicates: N` и ничего не меняет в базе |
| Битое событие не ломает пачку | каждое событие валидируется и вставляется отдельно, в `try/catch`; отбракованное уходит в `event_rejects` |
| Сырые ответы не попадают в аналитику | см. ниже |

### Что именно не попадает в аналитику

`answer_submitted` несёт не ответ пользователя, а его обезличенную проекцию
(`shared/src/privacy.ts`):

- `single_select` / `multi_select` → только `value` выбранных опций (это
  перечисление из конфига, а не пользовательский ввод) и количество выбранных;
- `number` → **бакет** по границам из конфига (`buckets`), например `5M-15M`
  вместо `12 000 000`.

Точные числа остаются в `sessions.answers_json` — операционной записи, которую
аналитический слой не читает вообще (ни один запрос в `analytics.ts` не
обращается к таблице `sessions`). Экран результата тоже рендерится на сервере:
правила выбора исхода читают сырые ответы, наружу уходит только текст.

Клиентская очередь (`web/src/lib/eventQueue.ts`) буферизует события, шлёт
пачками по 6 штук или раз в 2,5 с, дублирует буфер в `localStorage` до
подтверждения и уходит через `sendBeacon` при закрытии вкладки. Неудачная
отправка ничего не выбрасывает — пачка ретраится как есть, и дедупликация по
`event_id` делает ретрай безопасным по построению.

## 5. Аналитический экран

`#/admin/analytics`. **Все показатели — по уникальным сессиям**
(`COUNT(DISTINCT session_id)`), а не по количеству событий.

| Показатель | Формула |
| --- | --- |
| Начали воронку | сессии с `session_started` |
| Увидели шаг X | сессии с `step_viewed`(X) |
| Прошли шаг X дальше | сессии с `step_completed`(X); для `result` — с `cta_clicked` |
| Конверсия шага X | прошли дальше / увидели |
| Отвал на шаге X | увидели − прошли дальше |
| Доля от начавших | увидели(X) / начали |
| Достижение результата | сессии с `result_viewed` / начали |
| CTR основного CTA | сессии с `cta_clicked` / сессии с `result_viewed` |
| Сквозная конверсия | сессии с `cta_clicked` / начали |
| Медиана до результата | медиана `min(result_viewed.client_ts) − min(session_started.client_ts)`, отрицательные отбрасываются |

### Почему это устойчиво

Агрегаты — это **мощности множеств сессий**, а не суммы событий. Отсюда:

- **повторные просмотры** (вернулся назад, снова увидел шаг) не раздувают
  воронку: сессия входит в множество один раз. Сами возвраты видны отдельной
  колонкой «повторные просмотры» и метрикой «возвраты назад»;
- **дубли событий** ничего не меняют дважды — и потому что до базы они не
  доходят (PK), и потому что даже дойдя, не изменили бы мощность множества;
- **порядок доставки** не используется ни в одной формуле. Событие, пришедшее
  с опозданием, попадает в то же множество. Блок «качество данных» отдельно
  показывает, сколько событий пришло не по порядку, — чтобы было видно, что это
  действительно происходит и действительно ни на что не влияет;
- **ветвление** не ломает воронку: у каждого шага свой знаменатель — те, кто его
  увидел. Шаг из редкой ветки показывает маленький охват и собственную
  конверсию, а не «провал» общей воронки.

**Ветвления** показаны отдельной строкой под шагом: сколько сессий, завершивших
шаг, затем увидели каждую из веток. Расчёт тоже множественный, поэтому сессия,
которая вернулась назад и сменила ответ, попадает в обе ветки — в интерфейсе это
подписано.

Срезы: фильтры по версии, варианту и `utm_campaign`, плюс готовые сравнения
A против B и версий между собой с дельтой в процентных пунктах.

Порядок шагов в таблице берётся из конфига (выбранной версии и варианта), а не
из данных. Поэтому шаг с нулевым трафиком виден как строка с нулями, а шаг,
которого в выбранной версии уже нет, помечается «нет в конфиге выбранной версии».

## 6. Генератор тестового трафика

```bash
npm run seed:traffic                               # 140 сессий, seed фиксирован
npm run seed:traffic -- --sessions 300 --seed 42   # больше и с другим зерном
npm run seed:traffic -- --url https://example.com  # против запущенного сервера
```

Генератор поднимает **настоящее Express-приложение** на свободном порту и ходит
в него по HTTP, то есть данные проходят ту же валидацию, то же закрепление
версии и тот же ingest, что и трафик из браузера. ГПСЧ — mulberry32 с зерном, так
что прогон воспроизводим.

Что он создаёт:

- 7 наборов UTM-меток, включая сессии вообще без меток (прямой трафик);
- оба варианта, плюс ~5 % сессий с явным override;
- распределение по двум последним опубликованным версиям: генератор временно
  переключает активную версию и в конце возвращает исходную;
- разные ветки (роль → операции/интеграции, объём → с бюджетом/без);
- отвал на разных шагах — «терпеливость» сессии зависит от качества кампании,
  поэтому у кампаний разная конверсия, а не шум;
- возвраты назад с повторным просмотром шага (~30 % сессий);
- ~12 % сессий отправляют одну и ту же пачку дважды (эмуляция ретрая);
- ~10 % кладут дубль `event_id` внутрь одной пачки;
- ~12 % перемешивают пачку, так что порядок доставки не совпадает с `client_ts`;
- ~6 % подмешивают заведомо битое событие (неизвестный тип, нечитаемая дата,
  отсутствующий `event_id`, несуществующая сессия).

В конце печатается сводка: сколько принято, сколько схлопнулось как дубли,
сколько отклонено. Эти же числа видны в блоке «Качество данных» на дашборде.

## 7. Модель данных

SQLite, одна миграция, ничего не удаляется.

```
funnel_versions(version PK, funnel_id, name, config_json, config_hash,
                source_file, notes, created_at)
funnel_active  (funnel_id PK, version → funnel_versions, updated_at)
version_audit  (id PK, funnel_id, action publish|activate|rollback,
                from_version, to_version, actor, note, at)

sessions (session_id PK, funnel_id, funnel_version → funnel_versions,
          variant, variant_source, created_at, updated_at, completed_at,
          current_step, answers_json, history_json, utm_*, user_agent)

events   (event_id PK, session_id, event_type, step_id, funnel_id,
          funnel_version, variant, client_ts, server_ts, utm_*, props_json)

event_rejects   (id PK, received_at, reason, event_id, session_id,
                 event_type, payload_json)
ingest_counters (key PK, value)
schema_meta     (key PK, value)
```

Три решения, которые стоит назвать явно:

1. **`events.event_id` — первичный ключ.** Идемпотентность не надстройка, а
   свойство схемы.
2. **Конфиги и `props` — JSON в TEXT.** Новый тип шага, новое событие и новый
   экран не требуют миграции. Именно поэтому вторая итерация публикуется и
   откатывается без изменения схемы.
3. **Сырые ответы живут только в `sessions.answers_json`.** В `events` их нет, и
   аналитический слой к `sessions` не обращается.

`ingest_counters` нужна потому, что дедупликация по природе бесследна:
`INSERT OR IGNORE` не оставляет строки. Счётчик — единственный способ показать на
дашборде, что идемпотентность действительно срабатывала.

## 8. Вторая итерация

Конфиг второй итерации — `configs/funnel.v3.json`. Что в нём изменилось:

1. **Добавлена условная ветка.** После экрана приоритетов появляется новый экран
   `sla` — но только если поток заказов `enterprise` **или** в интеграциях
   выбрана собственная legacy-система:
   `any([volume = enterprise, integrations includes legacy])`.
2. **Для варианта B удалён экран.** `removeSteps: ["warehouses"]`. Входящие
   переходы перевязываются автоматически: ветка роли, которая вела на
   `warehouses`, теперь ведёт на следующий шаг этой ветки. Висящих ссылок на
   удалённый шаг в резолвленном конфиге не остаётся — это проверяется и при
   публикации, и тестом.
3. **Появилось новое событие** `hint_expanded` — раскрытие подсказки на шаге.
   Новых таблиц и колонок не потребовалось.
4. **Старые активные сессии продолжают работу.** Сессия на v2 остаётся на v2,
   никогда не попадает на новый экран `sla` и штатно доходит до результата.

### Как проверить вручную

```bash
npm run seed:versions && npm run seed:traffic && npm run build && npm start
```

1. Открыть воронку, пройти два-три шага — сессия на v2.
2. На `#/admin` нажать «Опубликовать и включить» у `funnel.v3.json` → появится v3.
3. Вернуться на вкладку с незавершённой сессией и обновить её: плашка сообщит,
   что сессия продолжается на v2 при активной v3, и воронка продолжится.
4. Открыть воронку в новой вкладке (или с `?reset=1`) — это уже v3. С
   `?variant=B` экрана с количеством складов не будет; при ответе «более 50 000»
   появится новый экран регламента.
5. На `#/admin` нажать «Откатить на v2». Журнал запишет действие как `rollback`.
6. На `#/admin/analytics` в сравнении версий остаются все три строки: данные v3
   никуда не делись.

Автоматически тот же сценарий проверяет `tests/second-iteration.test.ts`
(9 тестов), включая неизменность схемы базы до и после публикации с откатом.

## 10. Деплой

Приложение — один процесс Node: он же отдаёт API, он же собранный SPA, рядом файл
SQLite. Для публичного URL нужна площадка с постоянным диском (serverless не
подходит: при эфемерной файловой системе база теряется между вызовами).

```bash
docker build -t funnel-runtime .
docker run -p 8787:8787 -v funnel-data:/data funnel-runtime
```

При первом старте сервер сам публикует `funnel.v1.json` и `funnel.v2.json`, если
база пустая, — задеплоенный URL работает сразу, без ручных шагов. Чтобы закрыть
админку, задайте `ADMIN_TOKEN`; токен вводится на самой странице управления.

### Render — бесплатный инстанс (манифест `render.yaml`)

1. На [dashboard.render.com](https://dashboard.render.com) → **New** → **Blueprint**.
2. Подключить GitHub и выбрать репозиторий. Render прочитает `render.yaml` сам.
3. `ADMIN_TOKEN` оставить пустым — иначе проверяющий не сможет опубликовать
   версию и сделать откат.
4. **Apply**. Первая сборка идёт несколько минут: ставятся зависимости и
   компилируется нативный `better-sqlite3`.

Карта не нужна. Но у бесплатного плана два ограничения, и оба обойдены:

**Нет постоянного диска.** Файловая система эфемерна, база исчезает при
перезапуске инстанса. Поэтому в манифесте задан `DEMO_SEED_SESSIONS=120`: при
старте на пустой базе сервер публикует конфиги и досевает синтетический трафик,
раскладывая его по двум версиям. Занимает ~4 секунды и идёт **после** открытия
порта, так что страница отвечает сразу. Повторный старт на непустой базе ничего
не делает.

**Инстанс засыпает после 15 минут простоя**, и холодный старт занимает около
минуты. Против этого — `.github/workflows/keepalive.yml`: пингует
`/api/health` раз в пять минут. Включается заданием переменной репозитория
`DEMO_URL` (Settings → Secrets and variables → Actions → Variables) со
значением вида `https://funnel-runtime.onrender.com`. Без переменной workflow
ничего не делает. GitHub отключает расписания в репозиториях без активности
60 дней.

Что честно теряется: сессии и публикации, сделанные во время просмотра, живут
до следующего рестарта инстанса. Сама логика откатов аналитику не теряет — это
ограничение эфемерного диска, и стенд предупреждает о нём баннером на
внутренних страницах.

**Вариант с постоянным диском** (нужен платный инстанс): в `render.yaml`
заменить `plan: free` на `plan: starter`, убрать `DEMO_SEED_SESSIONS`, задать
`DB_PATH=/data/funnel.db` и раскомментировать блок `disk:` — он там описан.

Наполнить стенд можно и снаружи, с локальной машины:

```bash
npm run seed:traffic -- --url https://<ваш-домен> --sessions 150
```

В режиме `--url` генератор не переключает версии, поэтому трафик ложится на
активную. Чтобы наполнить вторую версию, переключите её на `/#/admin`, повторите
команду и верните активной прежнюю.

### Fly.io (манифест `fly.toml`)

```bash
fly launch --no-deploy          # подхватит fly.toml
fly volumes create funnel_data --size 1
fly deploy
```

Одна машина и один том: SQLite требует единственного писателя, поэтому
`min_machines_running = 1` и масштабирование репликами не предполагается.

## 12. Агентский процесс

Работа велась в Claude Code одним управляемым потоком, без параллельных агентов:
задача сильно связная — доменное ядро, бэкенд, фронтенд и тесты переиспользуют
одни и те же типы и инварианты, и параллельные агенты здесь создали бы больше
рассогласований, чем выигрыша. Декомпозиция шла по слоям:
`shared` → конфиги → бэкенд → фронтенд → генератор → тесты → вторая итерация,
каждый слой проверялся до перехода к следующему (`tsc -b`, запуск, тесты,
проверка в браузере).

Что было поймано при ревью сгенерированного кода, а не тестами постфактум:

- **Зацикливание в варианте B.** В v2 и v3 вариант B переносит вопрос о
  приоритетах выше по потоку, но `next` у шага объёма заказов остался указывать
  на уже пройденный экран приоритетов. Оба конфига переписаны, у v3 новая ветка
  перевешена на шаги, где нужный ответ уже собран.
- **Бэктик в SQL-комментарии** внутри шаблонной строки с DDL — закрывал литерал.
- **`duplicate_submissions_blocked` всегда 0.** Дедупликация через
  `INSERT OR IGNORE` бесследна, считать её постфактум не из чего. Добавлена
  таблица `ingest_counters`.
- **Переаттрибуция ветки.** Распределение по веткам считается множествами, и
  сессия, вернувшаяся назад, попадает в обе — вместо того чтобы прятать это,
  оговорка вынесена в интерфейс.
- **`event_id` короче 8 символов.** Пять тестов упали на собственной валидации.
  Правило оставлено (оно ловит реальный класс ошибок — клиент с тривиальным
  id молча схлопнул бы весь поток), но сообщение сделано явным, а фикстуры
  приведены к реалистичным id.

## 13. Ограничения и допущения

**Допущения.**

- Конфиги написаны самостоятельно: к заданию прилагался только `.docx`.
- Одна воронка (`FUNNEL_ID`). Схема это поле уже несёт, мультиворонка — вопрос
  роутинга, не модели данных.
- Админка открыта, пока не задан `ADMIN_TOKEN`. Полноценной аутентификации нет —
  в задании она не требовалась.
- `step_completed` считается признаком «прошёл шаг дальше». Для экрана
  результата такого события нет, его роль играет `cta_clicked`.
- `session_started` пишет сервер. Иначе блокировщик или неудачный beacon
  занижали бы знаменатель всех конверсий.
- Порядок событий восстанавливается по `client_ts`. Он используется только для
  времени до результата и для счётчика «пришло не по порядку»; ни один агрегат
  от него не зависит.

**Ограничения.**

- Дашборд не считает статистическую значимость: на синтетических объёмах это
  давало бы ложную уверенность. Показываются абсолютные числа и дельта в п.п.
- Один SQLite-писатель. Для нагрузки нужен отдельный ingest с очередью, но
  задание явно ограничивает хранилище SQLite или файлами.
- Распределение по веткам может давать сумму больше числа завершивших шаг —
  из-за возвратов со сменой ответа. Это оговорено в интерфейсе; точная
  атрибуция «последней выбранной ветки» потребовала бы восстановления
  последовательности, то есть доверия к `client_ts`.
- Фильтр по датам есть в API (`from` / `to`), в UI не выведен.
- Публикация доступна только из `configs/`; произвольный JSON принимает API
  (`POST /api/admin/versions` с телом `config`), но формы для него в UI нет —
  визуальный редактор по условиям задания не требовался.
- Очередь событий в браузере хранит до 200 событий в `localStorage`. В приватном
  режиме она деградирует до in-memory, и события незакрытой вкладки могут
  потеряться.
